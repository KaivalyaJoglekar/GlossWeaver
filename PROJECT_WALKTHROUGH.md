# GlossWeaver: complete project walkthrough

This document explains what GlossWeaver does, how information moves through the
codebase, what experiments E0 through E4 mean, which models are used, how the
models are trained and evaluated, where outputs are stored, and what the current
limitations are.

## 1. The project in one minute

GlossWeaver accepts **textual, ASL-gloss-style tokens** and reconstructs a fluent
English sentence.

```text
Input:  ME GO STORE YESTERDAY
Output: I went to the store yesterday.
```

In simple terms, the input contains the important concepts but often omits
English function words, inflection, and conventional word order. The model tries
to preserve the meaning while restoring items such as articles, prepositions,
pronouns, tense, agreement, and word order.

Technically, this is a **text-to-text sequence generation** project. The learned
systems fine-tune encoder-decoder Transformer models from the T5 family. It is
not a video-to-text system and does not perform pose estimation, hand tracking,
sign recognition, or speech synthesis.

## 2. Important terminology

- **Gloss:** a written token-level representation associated with signs, such as
  `WOMAN BUY CAR RED`. The project works with gloss-like text, not raw signing.
- **Target/reference:** an acceptable fluent English rendering, such as
  `The woman bought a red car.`
- **Checkpoint:** saved model weights, tokenizer files, and configuration after
  training.
- **Experiment:** one controlled stage in the model-development sequence. E0 to
  E4 are experiment labels, not five unrelated foundation models.
- **Auxiliary grammar objective:** an additional training signal that asks the
  encoder to predict which grammatical operations are needed.
- **Weak label:** a label generated by rules rather than manually annotated by a
  linguistic expert. It is useful but should not be treated as ground truth.
- **Inference:** running a trained checkpoint on new gloss input.

## 3. End-to-end flow

```text
Raw ASLG-PC12 + clean reconstruction sources
                    |
                    v
        clean, deduplicate, split, audit
                    |
                    v
       {gloss, English target, grammar labels}
                    |
                    v
 shared instruction formatter + SentencePiece tokenizer
                    |
                    v
       T5/FLAN-T5 encoder-decoder training
                    |
                    v
             saved checkpoint
                    |
          +---------+---------+
          |                   |
          v                   v
  CLI/evaluation       FastAPI -> React UI
          |                   |
          +---------+---------+
                    v
        the same Reconstructor class
```

All active training, evaluation, command-line, API, and UI-backed inference use
the same input instruction:

```text
Convert this gloss-like text into a fluent English sentence: <GLOSS>
```

This shared formatter is important because a mismatch between training prompts
and serving prompts can make a good checkpoint appear broken.

## 4. What E0, E1, E2, E3, and E4 mean

The experiments form a progression. Each stage answers a different research
question.

| Stage | System | Initialization | Training data | Grammar objective | Purpose |
|---|---|---|---|---|---|
| **E0** | Copy heuristic | None | None | No | Establish a non-learned lower bound |
| **E1** | T5-small | `google-t5/t5-small` | 5,000 ASLG-PC12 pairs | No | Test a basic domain-specific fine-tune |
| **E2** | FLAN-T5-small hybrid | `google/flan-t5-small`, then staged continuation | 10,000 mixed pairs | No | Test better initialization plus product-relevant data |
| **E3** | Grammar-aware FLAN-T5-small | Passing E2 checkpoint | Same 10,000-pair mix | Yes, weight 0.1 | Isolate the effect of auxiliary grammar supervision |
| **E4** | Final GlossWeaver model | E3 checkpoint | 37,388 mixed pairs | Yes, weight 0.1 | Scale the best recipe; current default |

### E0: copy baseline

E0 is not a neural model. It extracts words, lowercases them, capitalizes the
first word, and adds a period.

```text
ME GO STORE YESTERDAY -> Me go store yesterday.
```

It preserves source concepts well, so content-word recall can be high, but it
does not genuinely reconstruct English grammar. This is why content recall must
not be interpreted alone.

Implementation: `src/glossweaver/modeling/baseline.py`.

### E1: T5-small trained only on ASLG-PC12

E1 fine-tunes `google-t5/t5-small` on a fixed 5,000-example ASLG-PC12 research
subset. It learns the source corpus well but generalizes poorly to short
household and school examples.

This was the key failure diagnosis: a model can score reasonably on held-out
ASLG text while still failing the intended product inputs. The problem was
primarily **domain mismatch**, not simply lack of model capacity.

### E2: FLAN-T5-small plus hybrid reconstruction data

E2 changes the initialization to `google/flan-t5-small` and mixes ASLG-PC12 with
clean telegraphic-to-English reconstruction pairs. The added data covers short,
compositional examples closer to the actual inputs.

E2 produces the largest recovery in the experiment sequence. Its challenge
BLEU rises from E1's 2.61 to 84.40. Therefore, the current evidence says that
better-aligned data and instruction-tuned initialization mattered more than the
custom grammar head.

The final E2 checkpoint includes staged continuation runs used to cover missing
constructions. It has seven total epochs across those stages, so E2 is not a
perfectly compute-matched comparison with every other row.

### E3: grammar-aware FLAN-T5-small

E3 starts from E2 and adds a linear multi-label classification head over the
mean-pooled encoder representation. During training, it predicts seven grammar
operations:

1. `ARTICLE`
2. `PREPOSITION`
3. `AUXILIARY`
4. `PRONOUN`
5. `TENSE_ASPECT`
6. `AGREEMENT_INFLECTION`
7. `WORD_ORDER`

Its loss is:

```text
total loss = sequence-generation loss + 0.1 * grammar BCE loss
```

The grammar head helps the encoder attend to transformations required between
the gloss and target. It is an auxiliary signal; the decoder still generates
the final English sentence normally. At inference time, the head also exposes
seven probabilities for inspection in the API/UI.

E3 improves the held-out ASLG and synthetic scores modestly but does not improve
the nine-example challenge BLEU over E2. It is therefore a helpful secondary
intervention, not the main reason the project recovered.

### E4: final scaled GlossWeaver checkpoint

E4 starts from E3 and uses the same grammar-aware architecture on the larger
mixed training set: 20,000 ASLG examples plus all 17,388 available synthetic
training examples, for 37,388 examples total. It trains for two configured
epochs and is the current default served model.

E4 is still based on **FLAN-T5-small**. “GlossWeaver” names the complete trained
system and recipe; it is not a new foundation-model architecture built from
scratch.

## 5. Current recorded results

All values below come from `results/tables/main_results.csv`.

| System | Train examples | ASLG BLEU | Synthetic BLEU | Challenge BLEU | Challenge content recall |
|---|---:|---:|---:|---:|---:|
| E0 copy | 0 | 20.24 | 21.48 | 11.93 | 1.000 |
| E1 T5-small / ASLG | 5,000 | 54.48 | 7.13 | 2.61 | 0.546 |
| E2 FLAN hybrid | 10,000 | 65.45 | 23.91 | 84.40 | 1.000 |

| E4 scaled recipe | 37,388 | 72.93 | 29.55 | 90.92 | 1.000 |

The ASLG and synthetic columns use deterministic 500-example test slices. The

The E4 challenge metrics are:

- SacreBLEU: **90.92**
- ROUGE-L: **0.956**
- METEOR: **0.953**
- BERTScore F1: **0.990**
- Content-word recall: **1.000**

These scores show that the current checkpoint handles this controlled set very
well. They do not establish human-level ASL translation: the challenge is tiny,
text-only, and was inspected during development. Although exact challenge
inputs and references are blocked from training-data leakage, the challenge
did influence diagnosis and augmentation design. It should be treated as a
development/acceptance set, not a fully untouched external benchmark.

## 6. Data used by the project

### ASLG-PC12

The pinned source is `achrafothman/aslg_pc12` at a fixed revision. The code
verifies that the orientation is `gloss -> English text` and expects 87,710 raw
rows. Cleaning produces 81,017 unique pairs and a deterministic seed-42 split:

- Train: 64,813
- Validation: 8,101
- Test: 8,103

ASLG-PC12 is useful at scale, but its content is rule-generated parliamentary
text and is not representative of naturally produced ASL conversations.

### Reconstruction supplement

The clean reconstruction corpus contains 21,785 quality-checked pairs across
public LibriSpeech-derived English and controlled compositional, conditional,
and schedule templates. English sentences are converted into clean telegraphic
inputs by removing selected function words and normalizing certain forms.

The builder checks for empty fragments, malformed inputs, duplicate targets,
and exact challenge gloss/reference leakage. Synthetic data increases domain
coverage, but templates are not a substitute for human-produced gloss-English
pairs.

### Challenge data

`data/challenge/glossweaver_challenge.csv` contains nine short inputs and three
acceptable references per input. Multiple references are important because
tense, articles, prepositions, and attachment can be genuinely ambiguous when
the source is underspecified.

## 7. How training works technically

1. A typed preset is loaded from `src/glossweaver/settings.py`.
2. The fixed seed is set and the requested tokenizer/checkpoint is loaded.
3. ASLG and optional reconstruction records are selected deterministically.
4. `GlossTextDataset` formats the input and tokenizes both source and target.
5. For E3/E4, seven weak grammar labels are attached to every record.
6. `Seq2SeqCollator` pads variable-length batches and uses `-100` for ignored
   decoder-label padding.
7. AdamW optimizes the model with a linear warm-up/decay schedule.
8. Validation generation loss controls best-checkpoint saving and early stopping.
9. The tokenizer, weights, model config, history CSV, and training metadata are
   written to disk.

Important shared defaults include seed 42, beam width 4 for reported inference,
maximum source/target length 96 during training, maximum 64 new output tokens,
no sampling, early stopping, and no repeated 3-grams.

The overfit checks train on only 64 examples. Their purpose is to verify that
the model, labels, batching, optimizer, and loss can learn a tiny dataset before
spending time on a full run. Recorded results were BLEU 94.27 for T5-small and
99.55 for FLAN-T5-small.

## 8. Evaluation parameters and what they mean

| Metric | What it measures | Main caution |
|---|---|---|
| **SacreBLEU** | Corpus-level n-gram overlap with reference text | Penalizes valid alternative wording |
| **chrF** | Character n-gram overlap | Still reference-form dependent |
| **ROUGE-L** | Longest-common-subsequence F1 | Rewards shared ordering, not full meaning |
| **METEOR** | Token alignment with some linguistic flexibility | Can miss role reversal or subtle semantic errors |
| **BERTScore F1** | Contextual embedding similarity | Semantic-looking similarity can hide factual errors |
| **Exact match** | Identical prediction and reference after trimming | Too strict when many English renderings are valid |
| **Content-word recall** | Fraction of source concepts present in output | A copied, ungrammatical input can score 1.0 |
| **Copy ratio** | Fraction of predicted content concepts copied from input | Diagnostic, not a quality score |
| **Grammar precision/recall/F1** | Whether each required grammar operation appears | Based on the same weak rule labeler, not human gold labels |

For the three-reference challenge, BLEU and chrF receive all reference streams;
ROUGE-L, METEOR, and BERTScore use the best matching reference per example.
Evaluation also records runtime, checkpoint path, example count, beam width,
dataset, split, and seed.

## 9. What happens during inference

For E1-E4, `Reconstructor` performs the following steps:

1. Resolve the requested key through the model registry.
2. Refuse unknown or missing checkpoints instead of silently loading another.
3. Normalize whitespace and add the shared instruction prefix.
4. Tokenize and move tensors to CPU, Apple MPS, or CUDA.
5. Generate deterministically with beam search; sampling is disabled.
6. Decode the generated token IDs into English.
7. For E3/E4, run the grammar head and return sigmoid probabilities.

The CLI and FastAPI backend both call this class. The API caches loaded models
and reloads a checkpoint if its weight-file timestamp changes.

## 13. What is fixed and what is still limited

### Fixed in the active model pipeline

- The `gloss -> English` orientation is explicitly verified.
- Training and all inference paths use one formatter.
- Model selection uses explicit registry keys and never silently substitutes a
  different checkpoint.
- Malformed suffix-stripping behavior is excluded from the active data recipe.
- Exact challenge glosses/references are checked against training data.
- Grammar labels are present for every grammar-aware mixed batch.
- Direct CLI and API inference have recorded parity.
- E4 is available and is the default checkpoint.

### Current research limitations

- The project has no large, independent, human-produced ASL gloss-English test
  set and no formal evaluation by fluent ASL users/interpreters.
- ASLG-PC12 is rule-generated parliamentary data, not natural conversational ASL.
- Much of the supplementary data is controlled or synthetic.
- The nine-item challenge is too small for broad claims and influenced model
  development even though exact training leakage is blocked.
- Reported ASLG/synthetic scores use 500-example slices rather than full tests.
- The principal results use one seed, so run-to-run variance is unknown.
- E2, E3, and E4 do not have perfectly matched training compute/data scale.
- Grammar labels are heuristic. The 200-pair audit found agreement of 1.00 for
  five structural labels, 0.70 for tense/aspect, and 0.55 for agreement.
- Gloss input may be ambiguous; no text-only system can recover information that
  is genuinely absent without making assumptions.
- Rare vocabulary, unusual syntax, very long inputs, malformed glosses, and
  domains far from training data remain risk areas.
- Automatic overlap/embedding metrics do not reliably detect every role reversal,
  hallucination, pragmatic error, or culturally inappropriate translation.

### Current product/UI limitations

- The inference tab uses the live model registry and E4 correctly.
- The current Metrics panel is stale: its short IDs (`e0`-`e4`) do not match the
  API registry keys, it expects a different response shape/metric names, it omits
  `WORD_ORDER`, and some displayed dataset descriptions are outdated. Until that
  panel is updated, use `results/tables/main_results.csv`,
  `results/tables/grammar_diagnostics.csv`, or the `/api/metrics/<model_key>`
  endpoint as the source of truth.
- The API is a research preview: permissive CORS, no authentication/rate limiting,
  local checkpoints, and no production monitoring or multi-user hardening.

## 14. What better data would improve next

The most valuable next step is not automatically a larger model. The E1-to-E2
jump already shows that data alignment is the dominant lever.

Recommended order:

1. Create an untouched, human-produced test set and do not use it for model or
   prompt decisions.
2. Collect/validate real gloss-English pairs from the intended user domain with
   fluent ASL experts and appropriate consent/licensing.
3. Add multiple acceptable references for ambiguous inputs.
4. Add minimal pairs that test subject/object roles, time expressions, spatial
   relations, negation, questions, classifiers, and discourse context.
5. Replace weak grammar labels with at least 1,000-2,000 manually reviewed labels
   and measure annotator agreement.
6. Report multiple random seeds, confidence intervals, full held-out sets, and
   human adequacy/fluency ratings.
7. Only then compare larger FLAN-T5 or other encoder-decoder backbones under
   matched data and compute.

Avoid treating outputs generated by the current model as unquestioned gold
targets; that can amplify its existing errors.

## 15. Bottom line

GlossWeaver is now a coherent text reconstruction pipeline with reproducible
configuration, explicit checkpoints, audited data construction, multiple
baselines, grammar-aware training, evaluation artifacts, and shared CLI/API/UI
inference. E4 is the strongest current checkpoint and is built by fine-tuning
FLAN-T5-small, not by training a new language model from scratch.

The recovery result is strong on the current controlled tests. The next major
research milestone is credible human-produced data and an untouched external
evaluation, followed by UI metric repair and production hardening if the system
is intended to move beyond a research preview.
